## [2026-08, pre-repo] Add Drafting Agent as a sixth pipeline stage
**Context:** The project was originally scoped and pitched as "Legal Aid Research & Drafting Assistant," but the planned pipeline only covered research (query analysis, retrieval, validity checking, reasoning, citation verification) — the "Drafting" half of the name had no corresponding stage.
**Decision:** Added a Drafting Agent (Agent 6) that generates legal documents from verified research, using a database of stored legal document templates/schemas so it can't hallucinate document structure. Its output is re-verified through the Citation Verifier Agent and gated behind explicit user approval before export.
**Why:** The product name and pitch promised drafting; without this stage the deliverable didn't match the claim.
**Trade-off:** Added a full agent and a template/schema database to the build plan (Module scope grew); the team kept calling it a "5-agent pipeline" in presentations for continuity even though it's actually six stages.

## [2026-08, pre-repo] Target US case law instead of Indian law
**Context:** The project was originally conceived as an Indian-legal-aid tool.
**Decision:** Pivoted to building and benchmarking against US case law (Caselaw Access Project / CourtListener corpora).
**Why:** The strongest available hallucination benchmarks and base papers (Dahl et al. 2024, Magesh et al. 2025) are US-specific — running their exact test queries against an Indian-only corpus would make the core benchmarking claim invalid. US corpora are also more readily available and pre-cleaned.
**Trade-off:** Indian-legal-NLP literature (ILDC, IL-TUR, IL-PCSR, InLegalBERT, IndicLegalQA) remains in the literature review for historical continuity even though it no longer matches the build target — a minor inconsistency between the lit review and the actual corpus.

## [2026-08, pre-repo] Scope down product feature set to pipeline-native features only
**Context:** Brainstorming explored a full multi-module "legal operating system" — Command Center, Case Binder/Graph Explorer, document redlining, etc.
**Decision:** Rejected the expanded product surface. Kept only features that reuse existing pipeline infrastructure: a trace panel, a verification badge, saved threads, thumbs up/down feedback, PDF/DOCX export, and a document-upload citation-audit feature.
**Why:** The expanded scope was too large for a 5-person, time-boxed college team project.
**Trade-off:** Defers a broader product vision (case management, graph exploration UI) to a hypothetical future phase; the MVP is deliberately narrower than what was discussed.

## [2026-08, pre-repo] React (Vite) + Tailwind CSS instead of vanilla HTML/CSS/JS
**Context:** The team's usual default for projects like this was plain HTML/CSS/JS.
**Decision:** Chose React (Vite) + Tailwind CSS for the frontend, not Next.js.
**Why:** The feature set (trace panel, verification badges, action-gate approval flow, live credits) involves too much interdependent UI state to hand-manage cleanly in vanilla JS. This decision was revisited once and confirmed to stand.
**Trade-off:** Higher frontend build complexity and tooling overhead than a static site, accepted in exchange for maintainable state management.

## [2026-08, pre-repo] Add Input & Sanitization Layer, Reranker, and Action Gate; defer MCP integration
**Context:** A reference architecture shared by the team's internship mentor (a GenAI real estate lease assistant with input sanitization, hybrid retrieval, reranking, and a supervision layer) was adapted for this project.
**Decision:** Added three things to the pipeline: (1) an Input & Sanitization Layer — PII filter, prompt-injection detection, scope check — in front of the Query Analyzer Agent; (2) a cross-encoder Reranker between the Hybrid Retriever and the Validity/Citator Agent, narrowing results to the top 3-5 passages; (3) an Action Gate requiring explicit user approval before any drafted document can be exported, as a third supervision outcome alongside auto-answer and abstain. MCP tool integration was explicitly deferred to future scope, not part of the current build.
**Why:** These closed gaps the reference architecture exposed: unsanitized input reaching agents, over-wide retrieval results reaching the reasoning stage, and no human checkpoint before an actionable document could leave the system.
**Trade-off:** Three additional architectural components to build and maintain (Modules 1.5 and reranker logic) versus the original simpler pipeline; MCP tooling is left unbuilt, so no external tool-calling capability exists yet.

## [2026-09-15] Replace CAP corpus source with the `common-pile` mirror
**Context:** The official Free Law Project CAP dataset on Hugging Face (`free-law/Caselaw_Access_Project`) is gated, and the access request sat in "pending" status, blocking programmatic pulls. CourtListener's own bulk data (`wiki.free.law`) was also considered, but it ships as raw PostgreSQL dumps split across multiple large CSVs (Courts, Dockets, Opinion Clusters, Opinions), requiring gigabytes of downloads and multi-table relational joins locally just to get text with metadata.
**Decision:** Switched the corpus source to `common-pile/caselaw_access_project` — an ungated, publicly accessible mirror of CAP/CourtListener data that streams without authentication as flat JSON text.
**Why:** Unblocks ingestion immediately with no auth wait and no local multi-table join work.
**Trade-off:** `common-pile` rows have sparse top-level metadata (only `author`, `license`, `url`). A regex header parser (`parse_case_header`) had to be built to extract `case_name`, `docket_number`, `court`, and `decision_date_raw` from the first 500-600 characters of raw opinion text — logic that wouldn't have been needed with CAP's structured metadata.

## [2026-09-15] Standardize on BAAI/bge-base-en-v1.5 (768-dim), run locally
**Context:** `BAAI/bge-small-en-v1.5` (384 dimensions) was considered for embedding speed, but the Supabase `case_chunks` table had already been created with a 768-dimension vector column.
**Decision:** Standardized on `bge-base-en-v1.5` (768 dimensions), run locally via `sentence-transformers` rather than through OpenAI or Openrouter.
**Why:** Matches the already-created schema without a re-migration; running locally avoids API rate limits, per-token cost, and network overhead during bulk ingestion.
**Trade-off:** Slower embedding throughput on local CPU hardware (a contributing factor in the corpus-size reduction below) versus a faster hosted embedding API.

## [2026-09-15] HNSW index instead of IVFFlat for pgvector
**Context:** The original plan specified `ivfflat (embedding vector_cosine_ops) WITH (lists = 100)`. IVFFlat requires pre-existing data to train its clustering lists and fails on an empty table.
**Decision:** Switched to an HNSW index (`CREATE INDEX ... USING hnsw (embedding vector_cosine_ops)`).
**Why:** HNSW builds dynamically with no training step and gives higher recall.
**Trade-off:** HNSW index builds are typically more memory-intensive and slower to construct at very large scale than a trained IVFFlat index — an acceptable trade at the current corpus size (502 cases), worth revisiting only if the corpus grows by orders of magnitude.

## [2026-09-15] Upgrade chunking to RecursiveCharacterTextSplitter
**Context:** Naive character slicing was the original chunking approach.
**Decision:** Adopted `langchain_text_splitters.RecursiveCharacterTextSplitter` (`chunk_size=2000`, `chunk_overlap=200`, separators `["\n\n", "\n", ".", " ", ""]`).
**Why:** Stops citations and legal terms from being cut mid-word/mid-citation, which naive slicing did not guarantee.
**Trade-off:** Adds a dependency (`langchain_text_splitters`) for what is otherwise a single-purpose utility.

## [2026-09-15] Normalize inconsistent dates with dateutil fuzzy parsing
**Context:** Raw text headers had inconsistent date formats (`Feb. 12, 1973`, `Jan. 18, 1973`, `March 1, 1973`).
**Decision:** Integrated `python-dateutil`'s `parser.parse(..., fuzzy=True)` to normalize these into proper SQL dates.
**Why:** Avoids leaving `decision_date` `NULL` for a large fraction of records, which would have degraded date-filtered retrieval.
**Trade-off:** Fuzzy parsing can silently misparse an unusual date string; no validation/audit step currently checks its output against the source text.

## [2026-09-15] Generate synthetic citation identifiers for corpus cases
**Context:** `common-pile` headers only expose docket numbers (e.g. `No. 72-1889`), not official reporter citations (e.g. `483 F.2d 1234`), but `cases.citation` is `NOT NULL UNIQUE`.
**Decision:** Generated synthetic identifiers in the form `"{docket_number} ({court} {decision_date_raw})"` to satisfy the constraint. Real reporter citations are deferred to a later backfill via the CourtListener API, planned for the Validity/Citator agent build.
**Why:** Unblocks ingestion without relaxing the uniqueness constraint or blocking on an external API integration mid-Module-1.
**Trade-off:** Synthetic identifiers aren't real Bluebook citations, so no internal citation edges can currently be detected in the citation graph (in-corpus citing/cited cases don't match reporter-format regexes) until the backfill happens.

## [2026-09-15] Citation graph built via regex extraction over raw text
**Context:** `case_citations` schema was ready; citation-graph population needed an extraction method with no external citation-parsing API in scope yet.
**Decision:** `scripts/build_citations.py` regex-scans each case's raw text for reporter-citation patterns and inserts an edge row per match, using `cited_case_id = NULL` with `cited_citation_text` capturing the raw matched string whenever the cited case falls outside the corpus (the large majority, as expected for a small 2-circuit corpus). Inserted 7,283 citation edges across the 502 cases this way.
**Why:** Gets a working citation graph populated without waiting on a more precise (and more complex) citation-parsing solution.
**Trade-off:** The original extraction regex (`\b(\d{1,4})\s+([A-Za-z\.\s]+)\s+(\d{1,4})\b`) is loosely specified and may include false positives, and the script isn't idempotent — re-running it duplicates rows. **Status: resolved 2026-09-25** (commit `bebfc7e`) — replaced with a `REPORTER_ABBREVIATIONS` allowlist regex and a delete-before-insert idempotency guard, per `CLAUDE.md` "First task" item 1.

## [2026-09-15] Schema drift confirmed: extra columns, surrogate PK, missing `overruled_by`
**Context:** Comparing the live Supabase schema against the original plan during Module 1 implementation surfaced several undocumented differences.
**Decision:** Accepted the live schema as ground truth going forward: `cases` has `source` and `created_at` columns beyond the original plan; `case_citations` uses its own surrogate `id` primary key rather than the originally planned composite key on `(citing_case_id, cited_case_id)` (confirmed necessary because the citation-population script inserts rows with `cited_case_id = NULL`, which a composite PK would reject since PK columns are `NOT NULL` by SQL standard); and the `overruled_by` self-referencing FK from the original plan was never added — only the boolean `is_overruled` flag exists.

Still unpopulated (by design); Module 4 falls back to dropping the overruled case when it's `NULL`.

## [2026-09-26] Replace keyword/regex scope and injection checks with embedding similarity
**Context:** Module 1.5's initial implementation used keyword lists for the scope check (legal-keyword allowlist + off-topic denylist) and a regex pattern list for prompt-injection detection. Post-build review (external second-opinion pass, not just self-review) surfaced real problems: (1) the off-topic denylist flagged genuinely legal questions that happen to touch an off-topic word, e.g. "What is the case law on movie piracy and copyright damages?" was rejected for containing "movie"; (2) keyword/regex injection detection is trivially bypassed by rephrasing and doesn't generalize; (3) a separate PII bug — the `ssn_alt` pattern (`\b\d{9}\b`) matched any bare 9-digit number, flagging non-SSN identifiers like EINs as PII; (4) `_is_legal_query`'s length-check branch was dead code (`if ... : return False` followed by an unconditional `return False`).
**Decision:** Replaced the scope check and injection check with embedding-similarity classification against small reference sets (`LEGAL_REFERENCE_QUERIES`, `OFF_TOPIC_REFERENCE_QUERIES`, `INJECTION_REFERENCE_QUERIES` in `sanitizer.py`), using the already-in-stack `BAAI/bge-base-en-v1.5` model (via a new shared `app/services/embedding_service.py`, avoiding a third copy-pasted `SentenceTransformer` instantiation alongside `ingest_corpus.py` and `test_retrieval.py`). Classification is nearest-neighbor cosine similarity (max similarity to any single reference example, not the cluster mean) — a flat cluster mean was tried first and produced false positives (e.g. "How do I make a chocolate cake?" scored as injection-like because averaging in a semantically distant legal-reference half diluted the benign-cluster mean); nearest-neighbor fixed this. Classification is a relative comparison (whichever cluster's nearest example is closer), not an absolute similarity cutoff. Dropped the `ssn_alt` pattern entirely rather than tightening it — the other PII patterns (SSN with dashes, phone, email, credit card) are genuinely pattern-shaped and stayed regex-based; only the bare-9-digit heuristic was removed.
**Why:** Embedding similarity judges topical/semantic closeness instead of substring presence, directly fixing the off-topic false-positive class of bug, and is strictly more robust to rephrasing than a regex/keyword blocklist for injection — at zero added recurring cost or new dependency, since `bge-base-en-v1.5` is already a required part of the confirmed tech stack for retrieval.
**Trade-off:** bge-base-en-v1.5 is trained for topical/semantic similarity, not adversarial-pattern detection, so injection detection specifically is a known softer spot than the scope check — it catches rephrasings of the reference examples but isn't adversarially robust (same caveat class as the synthetic `citation`/`is_overruled` values already noted for this corpus). The scope/injection reference sets now need occasional expansion as new false positives/negatives are found, rather than being "done." Sanitizer tests now load a local ML model on first run (a few seconds, already a hard dependency), versus the previous pure-regex tests being instant with zero setup; CI (`pytest -m "not integration"`) now downloads/loads `bge-base-en-v1.5` for `test_sanitization.py` too, not just the excluded `integration`-marked retrieval test — acceptable since it needs no live credentials. **Status: resolved 2026-09-26** — added an `actions/cache@v4` step for `~/.cache/huggingface` in `.github/workflows/ci.yml`, keyed to the model name, so only the first CI run after this change pays the ~440MB download cost.

**Known limitation, not yet hit in testing:** nearest-neighbor classification is a forced binary choice (argmax of two similarities) with no "neither / low confidence" outcome — a query far from both reference clusters (e.g. gibberish) still gets assigned to whichever cluster's nearest example happens to be marginally closer, purely by embedding geometry. For the scope check this defaults safely (off-topic is the safe failure direction). For the injection check it is **not** guaranteed to default safely — an ambiguous query lands in whichever bucket the raw similarity favors, not "benign" by design. If a false-negative injection is ever observed in testing, this forced-choice behavior — not the reference set content — is the first place to look.

## [2026-09-26] Sparse search indexes case_chunks.chunk_text, not cases.raw_text
**Context:** The Module 3 (Hybrid Retrieval Agent) brief specified the sparse full-text search RPC (`keyword_search_case_chunks`) as `to_tsvector('english', raw_text)` -- `raw_text` is a column on `cases` (the full opinion text), while dense search (`match_case_chunks`) operates at `case_chunks` (chunked) granularity and returns `CaseChunk` rows.
**Decision:** Built the GIN index and `keyword_search_case_chunks` RPC over `case_chunks.chunk_text` instead of `cases.raw_text`.
**Why:** Reciprocal Rank Fusion needs both branches ranking the same units so they can be merged by shared `id`. Indexing `cases.raw_text` would return one row per case (case-level granularity), which cannot be fused against `case_chunks`-level dense results, cited-graph-boosted, or returned as `CaseChunk` objects without an arbitrary case-to-chunk remapping step the brief didn't ask for.
**Trade-off:** None functionally -- `chunk_text` is the chunked slice of the same `raw_text` content, so full-text matches are still found, just anchored to the correct chunk. Matches the existing precedent of `match_case_chunks` already operating at chunk granularity for the same reason.

**Why:** Can't construct a live test case for a code path the live data has no rows for. The mocked tests exercise the actual substitution logic (batched replacement-chunk fetch, `CaseChunk` construction, fallback-to-drop when the replacement has no `chunk_index=0` row) faithfully against the real function, just not against real Supabase rows.
**Trade-off:** Substitution correctness against real data (e.g. real UUID formatting quirks, RLS policy interactions on the `overruled_by`-populated case) remains unverified until `overruled_by` is populated for at least one row — planned as part of the real Shepard's/KeyCite backfill before Module 16 benchmarking, same timeline as the `is_overruled` real-data fix.

## [2026-09-26] Sparse search used AND-only query semantics, returned 0 rows for realistic queries
**Context:** Post-Module-3 manual verification (retrieving on the two hand-picked integration queries and eyeballing which results carried a `sparse_rank`) found that `keyword_search_case_chunks` returned 0 rows for both natural-language test queries — e.g. "Fourth amendment unreasonable search and seizure of vehicle without warrant" — despite the RPC itself working correctly on short, literal queries (e.g. "search seizure vehicle warrant" returned 20 rows). Both the mocked test suite and the Module 3 integration tests had passed throughout, because the mocks never exercise the real SQL and the integration tests only assert `len(results) > 0`, which dense-only results satisfied on their own — sparse contributing nothing was never actually checked by any automated test.
**Decision:** Traced the cause to `plainto_tsquery('english', query_text)`, which joins every parsed term with `&` (AND) — a ~10-word natural-language legal question requires all ~10 stemmed terms to appear in a single chunk, which almost never happens. Fixed via a new migration (`0003_fix_keyword_search_or_semantics.sql`, since `0002` was already applied and migrations aren't edited post-application): cast `plainto_tsquery`'s output to text, replace `' & '` with `' | '`, and re-parse via `to_tsquery`, converting the query to OR semantics while keeping `plainto_tsquery`'s stemming/stopword normalization. `ts_rank` still scores chunks matching more terms higher, so ranking quality isn't flattened by the switch to OR.
**Why:** Sparse search is meant to be a keyword-overlap complement to dense semantic search in the RRF fusion; AND-only semantics made it fire only on short, near-exact queries, which defeats its purpose for a system meant to handle realistic natural-language legal questions. Re-verified post-fix: the same natural-language query now returns 20 rows from the raw RPC, and 20/20 fused results carry a `sparse_rank` (previously 0/20).
**Trade-off:** None identified — OR semantics with rank-based ordering is standard practice for this exact failure mode (it's the documented workaround for `plainto_tsquery`/`websearch_to_tsquery` not offering a native "soft AND" mode). Flagging as a process gap rather than a code trade-off: neither the mocked suite nor the integration tests would have caught a regression here, since both only check that fusion logic works given RPC output, not that the RPC returns non-trivial output for realistic queries. Worth adding an integration assertion that fails if `sparse_rank` is `None` across all results for a known query, so this can't silently regress.

## [2026-09-26] Fixed dangling out-of-range citation markers in reasoning output
**Context:** `_extract_citations` correctly excluded out-of-range `[N]` markers (a hallucinated reference beyond the numbered source list) from the `citations` list, but the literal marker text was left untouched in the displayed `issue`/`rule`/`application`/`conclusion` fields -- an unbacked, dangling citation marker visible in output.

## [2026-09-26] Module 6 uses LLM-based entailment judgment, not a local NLI cross-encoder
**Context:** Module 6 (Citation Verifier Agent, `backend/app/services/citation_verifier.py`) is the project's core correctness mechanism -- the only module ever permitted to mark a citation "verified" -- so its verification method needed a deliberate, traceable choice rather than defaulting silently to whatever was fastest to build. Two real options existed: (1) a local NLI/entailment cross-encoder (e.g. a sentence-transformers cross-encoder fine-tuned for entailment, similar in spirit to the Module 3.5 reranker's `bge-reranker-base`), scoring (claim, source) pairs with no LLM call and no Openrouter cost; (2) a single PydanticAI Agent call per reasoning result, batching every marker across all four IRAC fields together.
**Decision:** Went with the LLM-based approach (option 2), per the module brief.
**Why:** Off-the-shelf NLI cross-encoders are trained on short, generic sentence pairs (SNLI/MNLI-style) and don't reliably handle the actual shape of this task: identifying *which specific claim* an inline `[N]` marker attaches to inside a full multi-sentence IRAC paragraph (not a pre-isolated single sentence), reasoning over legal-domain language and citation-heavy text (periods inside "U.S.", "F. Supp. 2d", "S. Ct." would already break any additional regex/sentence-boundary preprocessing, which is exactly why marker-to-claim identification is delegated to the model's own contextual reading rather than extracted mechanically), and grounding a written explanation in the specific quoted source text rather than just emitting a bare label. A general-purpose LLM call handles claim identification, entailment judgment, and grounded explanation generation as one coherent step; a cross-encoder would only give the middle piece; and both this project's core papers (Dahl et al. 2024, Magesh et al. 2025) and the LePhantomCite methodology this module is benchmarked against evaluate citation-checking as a reading-comprehension task, not a generic sentence-pair classification task.
**Trade-off:** Real per-call Openrouter cost and latency versus a free, instant local cross-encoder (same cost/speed trade the reranker deliberately avoided by staying non-LLM) -- acceptable here specifically because this is the module whose whole job is judgment quality, not throughput, and it's batched as one call per reasoning result rather than one call per citation. Also means verification quality is coupled to the chosen model's reasoning ability and could vary by Openrouter model swap; `citation_verifier_model` is its own independently-configurable setting (separate from `query_analyzer_model`/`structured_reasoning_model`) specifically so this can be tuned or swapped without touching the other agents.

**Implementation note (fills in unspecified detail, not a deviation):** multi-marker claims (e.g. "...[1][3]") need OR-logic aggregation (the claim is satisfied if *any* cited source verifies it) while still reporting one verdict per marker. Since claim boundaries aren't reconstructed from the LLM's response, `_extract_marker_groups` deterministically scans the IRAC text for back-to-back bracket sequences with no separating text (e.g. `[1][3]`) and treats each such sequence as one OR-group for aggregation purposes -- a positional scan, not sentence-splitting, so it's unaffected by periods in abbreviations/citations. A marker the LLM's response omits entirely (shouldn't happen given the prompt's "return exactly one verdict per distinct marker" instruction, but not structurally prevented) defensively resolves to `UNVERIFIED` rather than being silently dropped from the `verdicts` list, consistent with the pipeline's abstain-over-fabricate posture.

## [2026-09-27] Structural claim/source-polarity comparison added to close a citation-verifier negation-blindness gap

**Context:** Post-Module-6 adversarial testing (LePhantomCite-style, per the citation-verification-precision claim planned for Paper 2) started with a corruption that prefaced a real claim with "Contrary to the source, ..." -- an obvious tell a weak verifier could catch via superficial lexical pattern-matching without ever really comparing claim content against source content, so it didn't actually prove entailment sensitivity. This directly bears on the core invariant that this module is the only one ever permitted to mark a citation verified.

**Decision:** First attempted a prompt-only fix: added an explicit, numbered directionality-naming-and-comparison step to `SYSTEM_PROMPT` (name the claim's directionality, name the source's directionality, compare explicitly, treat a reversal as CONTRADICTED even with accurate surrounding detail) without changing the output schema. This confirmed prompt engineering alone was insufficient: trusting the model to both extract a claim's polarity and compare it against the source's polarity in one holistic pass is unreliable, even when explicitly instructed to perform the comparison.

Moved to a structural fix: added three fields to the internal `_VerdictDraft` schema only (the public `CitationVerdict`/`CitationVerifierResult` types are unchanged) -- `isolated_claim: str` (a fresh, in-isolation extraction of the specific clause tied to each marker), `claim_polarity: Literal["AFFIRMATIVE", "NEGATIVE"]`, and `source_polarity: Literal["AFFIRMATIVE", "NEGATIVE"]` (the same judgment applied to the corresponding source excerpt). The full mocked suite (79/79) shows no regressions across the four existing verdict paths, but mocked tests only prove the code-level override logic and aggregation are wired correctly, not that the real model's own `isolated_claim`/polarity extraction generalizes beyond the two live cases tested so far.

## [2026-09-27] Module 7 ablation toggles resolve deferred skip-behavior decisions from Modules 3.5, 4, and 6 in one place

**Context:** Three earlier, already-completed modules each explicitly deferred a "can this stage be skipped, and what does skipping mean for what's downstream" decision to pipeline orchestration: the reranker (Module 3.5) never decided whether validity checking should ever see raw, unreranked candidates; the validity checker (Module 4) never decided whether reasoning should ever run over unchecked candidates; the citation verifier (Module 6, whose header comment states it is the only module ever permitted to mark a citation "verified") never decided what happens to a reasoning result if verification never runs at all. Module 7 is the first point in the codebase with enough context to answer all three, since it is the only layer that sees the full stage sequence and what each stage's output feeds into next.

**Decision:** Added `PipelineDeps` (`enable_reranker`, `enable_validity_check`, `enable_citation_verification`, all default `True`) to `backend/app/services/pipeline.py`. Disabling a stage passes its input straight through unchanged to the next stage (e.g. disabling the reranker means the validity checker receives retrieval's raw candidate list, not a re-sorted or truncated one) rather than substituting a fake/default output. Every stage, skipped or not, gets a `PipelineTraceEntry`; a skipped stage is recorded with `skipped=True` and empty `data` so its absence is visible in the trace rather than silently missing. `citations_verified` is only ever set `True` when citation verification actually ran and returned `AUTO_ANSWER` -- never when the stage was skipped, so a skipped-verification `ANSWERED` result can never be mistaken for a verified one downstream (in the API response, the frontend's verification badge, or the ablation study itself).

One additional judgment call beyond the toggles themselves: when `enable_citation_verification=False` and the Reasoning Agent itself reports `insufficient_sources=True`, the pipeline returns `ABSTAIN` with the Reasoning Agent's own `insufficient_sources_reason`, rather than a literal `ANSWERED` with null/empty IRAC fields. This is a deviation from the module's task description, which named `AUTO_ANSWER` (or "verification skipped") as the two `ANSWERED` triggers without carving out this case explicitly.

**Why:** Centralizing all three toggles in the orchestrator (rather than, say, letting each stage take its own `enabled: bool` parameter) keeps every skip-semantics decision in one auditable place instead of splitting "what does skip mean" across three separately-completed modules' source files, and matches how the future ablation study (Module 16) actually wants to run: with-stage vs. without-stage comparisons driven from one caller, not three. On the `insufficient_sources` deviation: `insufficient_sources` is a no-answer signal from the Reasoning Agent regardless of whether citation verification runs afterward -- treating it as `ANSWERED` just because the ablation toggle happened to disable the next stage would mean the ablated pipeline reports a false "answered" outcome that the full pipeline would never produce for the same underlying reasoning result, which would corrupt exactly the ablation comparison this trace log exists to support.

**Trade-off:** None identified for the toggle design itself. The `insufficient_sources` carve-out means the ablated (`enable_citation_verification=False`) pipeline's `ANSWERED`/`ABSTAIN` split is not a pure function of "did verification run" alone -- it also depends on the Reasoning Agent's own judgment, which is arguably the correct behavior but is worth flagging explicitly since it wasn't spelled out in the module's original task description.

**Note on live-integration flakiness observed during testing -- known intermittent risk, not just infrastructure noise:** one integration run of `test_live_false_premise_query` raised `pydantic_ai.exceptions.UnexpectedModelBehavior: Exceeded maximum output retries` from inside `citation_verifier_agent` (Module 6). Re-running the identical test in isolation immediately afterward passed cleanly (`ANSWERED`, fully verified). Since the failure is tied to the specific shape of the multi-marker `verdicts` schema rather than to random infra timing, it is plausibly a recurring pattern under that schema shape with this model/provider, not pure one-off noise -- pydantic_ai's built-in single retry happened to self-heal it this time, and nothing about it implicates the polarity-comparison override or verdict-aggregation logic. No code change made now; flagged as a known-intermittent-risk to watch, not resolved. If it recurs with any frequency in practice, the fix is typically a stricter schema/field description or a str-tolerant coercion step ahead of validation in `citation_verifier.py` -- not a redesign.

## [2026-09-27] Drafting Agent: one PydanticAI agent call per required section, each scoped to a subset of the IRAC research

**Context:** Module 8's task description requires one agent call per required section rather than one call for the whole document, and requires each call's context to be "scoped to that section's relevant portion" of the IRAC research and verified_chunks.

**Decision:** `draft_document()` loops over every section in the template's `structure_schema` where `required=true` and makes one independent `section_drafter_agent.run_sync()` call per section. A keyword-based lookup (`_relevant_irac_fields`) maps each section's name (e.g. "Statement of Facts", "Argument", "Prayer for Relief") to the subset of the four IRAC fields (issue/rule/application/conclusion) actually relevant to it, defaulting to all four for an unrecognized section name. The numbered source list shown in each section's prompt is further narrowed to only the `[N]` markers that actually appear within that section's relevant IRAC field(s) (falling back to the full source list if none are found), rather than always showing the full verified_chunks list to every section call. Non-required sections (`required=false`) are not drafted and do not appear in `content_json` -- a future template with genuinely optional sections would need a separate mechanism to draft them, which does not exist yet.

**Why:** A single whole-document LLM call would force one model response to juggle every section's distinct tone, purpose, and relevant authority at once, and would make the "citation injector only pulls from verified_chunks" guarantee much harder to enforce section-by-section. Scoping each call's context to its own section keeps prompts focused, keeps citation markers grounded in the research that's actually pertinent to what's being drafted, and keeps failures localized (an empty or unfilled section is attributable to exactly one call, not the whole document).

**Trade-off:** The keyword-to-field mapping is heuristic, not derived from the templates' own data -- a future template with an unusually-named section (e.g. neither "Argument" nor "Discussion") falls back to seeing the entire IRAC result, which is safe (no worse than before) but not actually scoped. Drafting N sections also means N separate LLM calls per document instead of 1, trading latency and cost for the isolation benefits above.

**Options considered:** (a) leave as-is for now, document the limitation, revisit later (e.g. alongside benchmarking); (b) change Module 6 to verdict per marker-*occurrence* (or per claim-group) instead of per distinct marker number, which the failing-claims loop already conceptually iterates toward (`claim_groups`) but currently discards by looking up a single global `verdict_by_marker[m]`; (c) some other approach.

**Resolution (2026-09-27):** Option (a) chosen -- left as-is. `citation_verifier.py` is unchanged. Module 8 is considered done with this documented as a known, conservative-not-unsafe limitation: a multi-section drafted document that legitimately reuses one source across several distinct sub-claims may report `verification_status="failed"` even when every individual use is well-supported, because Module 6 still judges one marker number once for the whole assembled document rather than once per occurrence. No core invariant is affected (nothing is ever marked "verified" incorrectly; the failure mode is strictly conservative). **Context:** Live testing of the Backend API (Module 9) post-deployment surfaced two bugs: (1) async route handlers calling synchronous PydanticAI functions that internally use `run_sync()` to start their own event loop, causing "RuntimeError: this event loop is already running"; (2) `add_credit()` function passing a literal string `"balance + 1"` to Supabase's `.update()` method, which Postgrest interprets as a string literal rather than SQL, causing "invalid input syntax for type integer".

**Decision:** 
1. **Async route fix:** Converted `/api/research` and `/api/draft` route handlers from `async def` to plain `def`. FastAPI runs synchronous handlers in a threadpool where PydanticAI's `run_sync()` can safely start its own event loop. Routes calling synchronous PydanticAI functions (`run_pipeline()`, `draft_document()` and their transitive callees) must be synchronous; routes with no PydanticAI dependencies remain async (e.g., `/threads`, `/export`).
2. **Credits system fix:** Created a new migration (`0006_add_credit_rpc.sql`) defining an atomic `add_credit(p_user_id UUID, p_amount INT) RETURNS BOOLEAN` RPC function (PL/pgSQL), symmetric with the existing `deduct_credit()` RPC. Updated `app/services/credits.py::add_credit()` to call this RPC via `client.rpc("add_credit", {...}).execute()` instead of attempting a direct UPDATE. This ensures atomicity and avoids the string-literal bug.
3. **Test fixes:** Updated `backend/tests/test_api.py`'s `FakeSupabaseClient.rpc()` method to mock both `deduct_credit` and `add_credit` RPCs, returning `_FakeScalarResult([True])` or `_FakeScalarResult([False])` (list format matching Supabase scalar response shape, not bare boolean). Fixed `check_and_deduct_credits()` in `credits.py` to extract the boolean via `response.data[0]` instead of `bool(response.data)` (which evaluates non-empty lists as truthy regardless of content).

**Why:** 
1. Async/sync mismatch: FastAPI's event loop is already running when an async route handler is invoked; PydanticAI's `run_sync()` tries to start a new event loop in that same thread, which Python forbids. Synchronous route handlers run in a threadpool, giving `run_sync()` its own clean OS thread where it can create an event loop.
2. Supabase RPC atomicity: The string-literal bug (and the fundamental race-condition risk of SELECT-then-UPDATE) is why the build plan specified atomic credit deduction via RPC in the first place. A symmetric add_credit RPC closes the symmetry gap and prevents the string-literal issue entirely.
3. Test fix: Response data from a scalar-returning Supabase RPC is a list `[value]`, not a bare scalar. `response.data[0]` extracts the boolean correctly; `bool(response.data)` always evaluates to True for any non-empty list, making all credit checks pass even when they should fail.

**Trade-off:** Converting `/research` and `/draft` to sync routes adds minimal latency per request (the threadpool context switch is negligible compared to the pipeline's actual work); this is the correct trade for correctness. No other trade-offs identified.

## [2026-09-27] Module 9: `research.py` never persisted the real pipeline trace (`_trace` vs `trace` attribute mismatch)

**Context:** `POST /api/research`'s thread-persistence step stored `trace_json` via `getattr(result, "_trace", None) or {}`. `PipelineResult`'s real field is `trace` (public, no underscore) -- `getattr` silently returned `None` for every request (since `_trace` never existed), and `None or {}` became an empty dict, so every `research_threads` row's `trace_json` was persisted as `{}` regardless of how much real trace data the pipeline actually produced. This silently broke `POST /api/draft`, which reconstructs `ReasoningResult`/`CaseChunk` objects from the stored trace -- found only when `/api/draft` failed against a real persisted thread.

**Decision:** Corrected to `"trace_json": {"trace": [entry.model_dump() for entry in result.trace]}` -- reading the correct attribute name and explicitly serializing each `PipelineTraceEntry` (a Pydantic object, not directly JSON-serializable) before insert.

**Why:** `getattr(obj, name, default)` fails silently on a wrong attribute name rather than raising -- exactly the kind of bug that a stricter direct attribute access (`result.trace`) would have caught immediately at implementation time via an `AttributeError`, instead of silently persisting broken data that only surfaced two steps later in a different endpoint.

**Trade-off:** None functionally. Worth flagging as a pattern: `getattr(..., default)` should be reserved for genuinely optional attributes, not used as a substitute for verifying the correct attribute name exists.
